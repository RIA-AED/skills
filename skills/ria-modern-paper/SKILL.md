# RIA 自用风格现代 Paper 插件开发

本文档规范 RIA 团队（ZTH/Zeroth 服务器）自用插件的开发约定。适用于面向最新版本 Paper 服务端、并默认兼顾 Folia 兼容性的现代插件开发。

文档中的条目大多属于推荐做法，不是硬性标准。只有明确写成「必须」「不允许」的要求才需要强制遵守；遇到与本文不一致的存量代码或特殊场景，按实际情况判断，不要为了「合规」去改动既有实现。

## 1. 平台与版本策略

除非用户明确要求，插件只考虑兼容新版本的 Paper 服务端，要在开发时就“为 Folia 准备好”，除非遇到复杂的技术困境，不然默认就完整支持 Folia 服务端。

Folia 把世界切片成多个 region 并行 tick，游戏的“主线程”不复存在——所有访问主线程数据的路径都必须经过对应调度器。在 Paper 上跑时这些调度器自动回退为 Bukkit 行为，因此一套代码同时兼容 Paper + Folia。文档见 https://docs.papermc.io/paper/dev/folia-support/

四类调度器及其适用场景：

- **`GlobalRegionScheduler`**：`server.getGlobalRegionScheduler()`。用于与任何区域无关的全局任务，如全局配置保存、跨区域广播逻辑。
- **`RegionScheduler`**：`server.getRegionScheduler().execute(plugin, location, runnable)`。用于在某坐标所属区域上执行操作，如改该位置的方块、读取该位置的区块数据。**不要用于实体操作**，因为实体可能在区域间移动。
- **`AsyncScheduler`**：`server.getAsyncScheduler()`。用于不依赖服务端 tick 的纯异步工作，如网络请求、数据库查询。
- **`EntityScheduler`**：`entity.getScheduler()`。用于操作实体本身（玩家、生物等），它会随实体跨区域迁移。如改玩家背包、给实体加效果、玩家自身位置的传送。

要点：Folia 的 region-specific 任务无法取消，设计时避免依赖 `cancel()`。事件回调可能在任意 region 线程触发，禁止假设“主线程”。跨坐标/跨实体传送不要直接 `player.teleport()`，要走 entity scheduler。

如需判断当前是否 Folia：

```java
private static boolean isFolia() {
    try {
        Class.forName("io.papermc.paper.threadedregions.RegionizedServer");
        return true;
    } catch (ClassNotFoundException e) {
        return false;
    }
}
```

同时必须在 `plugin.yml` 或 `paper-plugin.yml` 中声明：

```yaml
folia-supported: true
```

具体兼容的游戏版本要看 RIA Zeroth 服务器的目标版本，目前是 Minecraft 26.1.2 版本（Mojang 于 2026 年起使用新版版本号命名法）。

## 2. Java 与 Adventure

Java 目标版本至少使用 25（Minecraft 26.1 开始使用 Java 25），因此你也可以安全放心地使用 Java 25 支持的任何特性，如果需要的话。

Adventure 在 Paper 中已经内置，在处理消息样式时，优先使用 Adventure（涉及可配置的 Message 时可以使用 MiniMessage）。同时，尽量使用 Adventure 5.x。如果你不熟悉 5.x，可以看文档 https://docs.papermc.io/adventure/migration/adventure-4.x/

关于具体的样式实现方式，需要分场景看待：

- 插件内部逻辑、面向管理或面向配置文件的消息，一般优先使用 MiniMessage 与 Adventure 组件。
- 但如果项目中还存在 legacy 的 `&` 颜色代码风格的存量代码，无需为了统一风格而强行迁改，可按实际情况分情况讨论。
- 在让普通玩家输入可能带有样式的消息时（例如自定义称号、聊天前缀等），应保留对 `&` 颜色代码的支持。MiniMessage 虽好，但玩家普遍更熟悉 `&` 形式的legacy 样式代码，贸然改用 MiniMessage 反而会给玩家带来使用负担。

## 3. 性能与异步优先

插件是异步优先的，在设计时就应考虑好性能，除对游戏内容的操作外，大部分操作都尽量不要暂停 Minecraft 主线程。对于任何网络请求、数据库链接、Redis 链接，更不允许在主线程上操作。

在 Folia 上“主线程”概念已不存在，但同理：任何会阻塞或耗时的操作应走 `AsyncScheduler`，所有对游戏状态（实体、方块、区块）的访问必须经过对应调度器。

## 4. 用户交互方式

除了使用 pastes 来和管理员交换复杂数据，和玩家交换数据你也可以使用点击式文字 ui 和 dialog。

### 点击式文字 UI

点击式文字 UI，是指在聊天框或成书中的可点击文字拼凑成的简单 UI，类似 TUI，但为了避免刷屏，不使用大量符号分隔，而是使用空格绘制 space，使用换行符和其他分隔。你可以使用 Adventure 轻松实现这些 UI。

但是在聊天框中绘制大量的 UI 不是一种轻松的解决方案，UI 通常是用完即走的，却在聊天框中留下了大量的刷屏信息，十分恼人。如果你要在聊天框中实现点击 UI，那么请尽量在不影响业务逻辑的前提下实现节流 throttle，避免用户手滑或者事件触发频繁导致刷屏。同时你还要实现 UI 尺寸的控制和一套命令，命令还需要有权限，还需要防止用户点击已经过时的 UI…… 这非常恼人，会带来大量的可维护性问题。

### Dialog（对话框）

因此，在 minecraft 1.21.6 更新后，我们可以使用更优质的对话框 Dialog 来实现用户交互。Paper 已经在 1.21.7 实现了实验阶段的对话 API，我们可以直接开始使用，无需担心未来的兼容性问题。Dialog 是一个全屏的弹出式 UI，能够实现文本组件的显示，按钮、布尔值、多选、文本录入、数字范围相关的 UI。这基本可以取代对话框 UI。甚至你也可以将文本点击式 UI 和对话框组合使用，因为对话框也能展示文本组件。不过要留意的是，dialog 是一种中断，它会给用户带来强打扰，不适用于轻量可忽略的交互需求。关于 Paper 对话框 API 的使用文档：https://docs.papermc.io/paper/dev/dialogs/

#### 排版要点

- **少拆组件，合并文本。** Dialog 里每个 body 组件（`DialogBody.plainMessage`、`DialogBody.item` 等）在客户端都自带上下边距，堆到 5～6 个就基本占满整个屏幕，正文没地方放，按钮还会被挤到看不见。因此尽量把说明文字合并进**同一个**文本组件，用 `Component.newline()` 或 `\n` 在组件内分行；需要分组时也在组件内用空行或列表符号排版，而不是拆成多个 `plainMessage`。
- **按钮标注层级。** 通向二级菜单的按钮在文案末尾加 `>`，如「设置 >」；从二级页面返回上一级的按钮写成「< 返回」。这样玩家不用点开就能分辨按钮是进入下一层还是返回上一层，多级菜单也能串得清楚。内容确实多时，优先拆成多级 dialog，而不是在一个界面里堆组件。

选择建议：轻量、可忽略、即用即走的提示走点击式文字 UI（注意节流）；需要录入、多选、确认的较重交互走 Dialog；二者可组合。

### 用 Dialog 做编辑器

当 Dialog 用来编辑数据（编辑轨道、配置条目等）时，除了上面的排版要点，还应注意：

- 不要把代码里的枚举名直接端给玩家；换成中文说法，需要时补一句悬浮说明。
- 上一页 / 下一页可以用 `<-` 和 `->` 标注，这样能找得更快。
- 有副作用的按钮要写清后果：如果「返回」实际是放弃修改，就写「取消」或「不保存并返回」。
- 涉及坐标的字段最好提供「传送到此」、「设置为当前位置」这类便利选项。
- 默认值选最符合直觉的选项。

### 与管理员交换复杂数据

如果你要和管理员进行命令和聊天框难以进行的数据交换，包括 YAML、JSON 等复杂数据的交换，你可以使用 pastes.dev。这是一个由 lucko 维护的 paste bin，但是更易于阅读和编辑，完全免费，API 友好。你可以在这里看到接口文档：https://github.com/lucko/paste/blob/master/API.md

## 5. 数据持久化

以上操作在绝大部分时候都不允许在主线程进行，因为它们都是很耗时的，任何在主线程上进行的网络请求或数据库链接都有卡死整个服务器的风险。

四种持久化思路：

1. 不需要跨服务器的数据，通常指玩家产生的数据，且数据涉及到的功能，没必要跨服共享或跨服共享反而可能带来问题的：存储到 yaml 中，尽量对不同类型的数据单独开一个 YAML 文件，不要和 Config 之类的非数据类的文件共用。设计存储时应留意并发安全和 mc 主线程性能。
2. 需要跨服的数据：使用 Redis。我们有一个持久化的 Redis 库，可以让你安全快捷地存储一些数据。但你也要留意，你正在开发的插件通常会在多个 paper 服务器上运行，如果某些数据的来源不是当前插件，如你需要同步服务器的在线玩家，那么这种数据就需要按服务端的概念隔离。你需要在插件的配置文件中维护一个 server-id。我们服务器的 server id 通常为一个字符串，如：zeroth、terminal-3。具体要怎么存储数据还需要和用户沟通。
3. 使用 Paper 的 pdc，persistent data container。如果你有一些和实体/方块强相关的数据，且这些数据通常在实体/方块被破坏后不再具有意义，那么也可以使用 pdc 来存储。但是玩家的 pdc 目前我们视为不可靠的，建议使用 uuid 为 key 通过其他方式存储。
4. 以上三种数据的存储方式通常已经够用，可以存储很多复杂的数据类型。但是如果开发的功能对 ACID 和结构化有十分强的要求，使用关系型数据库带来的收益远大于维护数据表的成本，那么你也可以使用 MySQL。

## 6. 命令与权限

插件应该实现完整的命令补全，级别是参数级。

### 帮助文本

帮助不是命令列表，需要有排版：

- 按功能分组，命令与说明分列对齐。对齐要按字体的像素宽度计算，不能按字符数，否则中英文混排会错位；每行控制在聊天栏宽度内。
- 每条命令可点击填入，悬停显示用法说明；只列出调用者有权使用的子命令。
- 参数细节放进单条命令的详情页，例如 `/插件名 help <子命令>`。
- `<必填>` 与 `[可选]` 的写法在帮助、详情和报错中保持一致。

### 命令命名

一般情况下，新建插件的命令建议以 /zth- 开头，如 /zth-preferences。这只是一个命名建议，并非硬性要求；如果命令本身已有合适的命名，或是在已存在的插件上增量开发，无需为了符合该前缀而改动既有命令。如果只是给管理员使用的命令，通常不需要再有其他 Alias。但是如果玩家也需要使用到这些命令，那么就必须要有好记的 Alias 如 /pref 等（尽量在英文上看起来美观，命令可以长，因为有 Tab 补全）。

### 权限控制

你实现的所有命令都需要有权限控制，需要确保没有权限的用户完全无法访问命令和补全。

你实现的命令和功能，大部分都需要权限节点。权限的设计，就按照优秀的 Paper 插件权限实践即可。对于面向管理员的功能或命令，一般配置 default op。对于面向全体玩家的功能或命令，一般默认也授予给玩家。

### 命名习惯

插件的命名按照正常习惯即可。如果你不知道这个插件应该叫什么，可以先问一下用户，避免插件的名称太偏离插件的主要功能。插件名一旦定下，会牵动包名、模块与目录名、命令、权限节点和配置文件名，事后改名成本很高。

Java 包名的根同样在开坑时确认：RIA 的域名是 ria.red，确定是 RIA 系的插件就用 `red.ria`；如果不是，先和用户确认。

权限节点的根节点取自插件自身名称的小写形式，再按功能分层，例如插件 `MySpawn` 对应 `myspawn.setspawn`、`myspawn.command.set`。当然这里提到的都是推荐的做法。既有插件的权限节点如果不满足以上要求，还按照它原本的风格即可。不要为了统一风格而改名，否则会让服务器上已经配好的权限失效。

对于 Zth 内部使用，完全不考虑其他服务器适配的插件，也可以使用 `Zth` 作为插件的开头。如果插件是为某年的特定活动而开发的，命名时把活动名与年份写进去，例如 `ZthSummerCamp2026Fishing`；不确定当届活动的正式名称时，同样先问用户。

## 7. RIA 风格的游戏内消息

除了前面提到的使用 Adventure 外，在设计插件的消息时要保持克制。不像传统的 Minecraft 服务器插件使用缤纷夺目的消息提醒，RIA 服务器尽量避免插件的消息打扰玩家。

插件对用户侧的消息优先使用中文。

本章给出的颜色与排版规范属于**建议**，主要适用于新消息的开发或大规模重构时对消息的重新设计，无需为了“合规”而逐一改动既有插件的存量消息代码。总体而言，只要不使用大量红色、绿色、蓝色、金色等鲜艳、刺激的颜色，其他偏柔和的配色体系一般都能接受。

### 历史由来

传统 Minecraft 服务器，尤其是中文服务器，通常采用色彩鲜艳的消息提示设计风格，偏爱使用红、黄、绿、橙等醒目的颜色。这往往是因为服务器管理员不愿花费精力进行消息提示的细致设计：许多服务器插件默认选择亮色作为消息提示色，而 Minecraft 服务器需要众多插件协同工作才能正常运行，这些插件的提示消息混杂在一起，导致聊天栏中充斥着五颜六色的信息，最终显得混乱不堪。

由于鱼头等人是平面设计等艺术领域的设计师，因此 RIA 自 ZTH 开服初期，游戏内提示风格就偏简洁冷淡。在 1.13.2 时期，游戏内消息的主色调以深灰色、灰色为主，这样的风格也成为了早期 ZTH 文化的一部分。

在笔者（Magma）接手 ZTH 服务端的维护工作后，ZTH 的所有插件配置基本上被推翻重造了一遍。相较于 Codusk，笔者更追求简洁但非性冷淡风格的设计，因此开始尝试使用浅灰、白色和少量蓝、绿或黄色的文本点缀，作为插件提示的配色风格。

在 1.16 版本中，Mojang 为游戏引入了 HEX 16 位色，Minecraft 自此可以在屏幕文字上显示更丰富的色彩。RIA 的开发者们也开始尝试引入平面设计领域的新颜色，作为浅灰和白色之外的点缀色，甚至出现了渐变效果和 Lore 中的字符画。以上种种最终演变为如今的 RIA 游戏内消息风格。

但由于插件和内容持续更迭，且 RIA 缺少明确的文档规范，部分开发者在刚开始设计消息色彩时会感到迷茫。本文旨在统一 RIA 游戏内消息的设计风格，让玩家在不同功能模块中获得一致的消息体验。

### 消息色彩的搭配

#### 聊天栏、ActionBar、Title 消息的颜色

- **普通积极结果的系统消息**：建议选用白色（`&f`）作为文字主色，重要关键词使用高亮色，如青蓝色（`&b`）或绿色（`&a`）。
  - 示例代码：`&f操作成功, 已收取 &a〇2&f.`
  - 视觉说明：整句主体为白色，货币数值“〇2”使用绿色高亮突出。
- **不重要的系统消息、普通错误提示**：建议选用浅灰色（`&7`）作为文字主色；不推荐搭配鲜艳高亮色，如需高亮优先使用白色（`&f`）。
  - 示例代码：`&7击杀幻翼, 发现幻翼掉落了一份礼物.`
  - 视觉说明：整句均为浅灰色，低对比度、低视觉干扰。
- **严重错误的系统消息**：推荐使用红色（`&c`）作为文字颜色。由于红色本身醒目度足够，不建议再叠加加粗或其他颜色进行强调。
  - 示例代码：`&c背包同步失败, 你的所有物品都不见了!`
  - 视觉说明：整句均为红色，依靠色彩本身传递严重警告的语义。

#### 物品文本的颜色

对于物品的名称与 Lore（描述文本），推荐使用浅灰色（`&7`）作为文字主色调；需要突出的内容可搭配协调的亮色，但点缀占比不宜过高。

RIA 的特殊物品通常带有统一落款（如活动产出物品），落款统一使用深灰色（`&8`），并以半角括号或尖括号包裹。

##### 示例 1：龙涎

- 名称：浅灰色（`&7`）文字「龙涎」
- 描述正文：浅灰色（`&7`）文字：从异种龙身上得到的散发着淡淡香气的诡异生物组织，你可以凭借它向我们换取一些报酬。现在的样本数量完全不够，快·去·工·作。
- 落款：深灰色（`&8`）文字：`(RCF样本-01)`

##### 示例 2：伤立停M高级版

- 名称：浅灰色（`&7`）文字「伤立停M高级版」
- 描述正文（全部为浅灰色 `&7`）：
  - 适用于小型伤口包扎
  - 功效：缓解伤痛、消炎止血，促进伤口愈合
  - <紧急医疗>系列
  - 由《薰风药业》制作
  - 由《星夜集团》发行

### 不打扰用户、低信息熵的排版

#### 高频操作消息的弱化处理

如果消息对应低成本、短时间内可能反复执行的操作结果，不建议使用白色或红色等高饱和度颜色，优先使用浅灰色（`&7`）。这类消息会在聊天栏高频刷屏，亮色会造成强烈的视觉疲劳；同时消息内容应尽量简短，避免换行。

> 反面效果示意：
> 大量重复、换行错乱的同类文本密集堆叠在聊天栏，文字破碎、排版混乱，对玩家造成极强的视觉干扰。

另一种优化方案是将反复出现的消息移入 **ActionBar**（快捷栏上方、屏幕中下位置的提示区域）展示。ActionBar 中的文字推荐使用默认白色（`&f`），关键字可加高亮色；不建议使用浅灰色，会降低可读性。

> ActionBar 示例：`&f点按右键即可打开掌上莉亚中心银行`
> 视觉说明：整句为白色，展示在快捷栏上方，不占用聊天栏信息流。

#### 单行优先原则

在内容足够简洁的前提下，良好的系统消息应控制在一行内。换行不仅增加阅读成本，在 Minecraft 排版能力有限的环境下，还容易导致消息与其他上下文混淆。

#### 图标与符号的使用

在 RIA 已有的游戏内消息中，常使用图标作为消息前缀，既可以区分不同的消息来源，也能作为通用辨识符号，丰富单调的文字排版。

> 格式示例：`&8<&7图标&8> &r`
> 视觉说明：尖括号为深灰色（`&8`），图标区域为浅灰色（`&7`），后跟 `&r` 重置格式，再接正文内容。

#### 分隔符规范

如果单条消息包含多组信息，可在信息之间加入分隔符，如 `|`、`/`、`·`。为避免分隔符喧宾夺主，建议将分隔符颜色设置为比主体信息暗一级：主体用浅灰（`&7`）时，分隔符用深灰（`&8`）。

> 示例代码：`&7在线 8(12) &8| &7TP5 20.0 &8| &735ms`
> 视觉说明：主体信息为浅灰色，三段信息之间的 `|` 分隔符为深灰色，视觉层级清晰，不抢正文注意力。

#### 使用更有中式气息的半角符号

如题，使用 `< >` 就要比使用 `[ ]` 在视觉上更加优雅。如果我有一个插件叫做 ZthFishing，那么我就可以把消息的开头写作 `&8<&7Fishing&8> &r`。当然，这不代表 `[ ]` 就不能使用。

#### 中英文混排空格规范

中文字符与数字、字母、符号或高亮关键词之间，应保留一个半角空格。中文本身无分词空格，但英文字母字形相对矮小，直接与中文衔接会造成视觉观感生硬，加空格可显著提升阅读舒适度。

> 错误示例（无空格）：
> - 你已经加入到Private频道
> - 未知的指令.请尝试/help或者问问万能的其他玩家.
>
> 正确示例（加空格）：
> - 你已经加入到 Private 频道
> - 未知的指令. 请尝试 /help 或者问问万能的其他玩家.

## 8. 依赖与外部库

插件自身不要 shade 依赖，除非确有必要。按依赖的性质分三种处理：

1. 依赖本身是另一个 Paper 插件（如 PacketEvents、PlaceholderAPI）：只在 `depend` 或 `softdepend` 中声明，不要打包进自己的 jar。
2. 普通的 Java 依赖：优先使用 Paper 内置的 `libraries` 机制在运行时下载，而不是塞进 jar。
3. 以上都不适用时再考虑 shade。拿不准的时候，先和用户讨论。

另外，避免直接写 NMS。插件写完之后通常不会有人定期维护，NMS 会随着服务端更新失效；优先使用稳定的 Paper API，或成熟协议库提供的封装。

## 9. 玩家状态与恢复

插件临时改动玩家状态（属性、游戏模式、飞行、药水效果、可见性等）时：

- 保证所有退出路径都能恢复：正常结束、玩家中途退出、服务器崩溃等。
- 假设第三方插件也会改动同一项状态，恢复逻辑要能应对这种情况，不要假设只有自己在改。
- 很多插件的越权漏洞都是因为没有考虑到某些边界情况，要避免因状态管理写出 BUG。Minecraft 是一个十分复杂的状态机。

## 10. 版本与发布

- 版本号遵循语义化版本；第一个正式版本从 `1.0.0` 开始，之后按改动性质递增。
- 每次发布在 GitHub 上打 tag 并创建 Release。
- 是否实现兼容层可以和用户确认，因为很多插件只有 RIA 自己的服务器使用，可以在上线前让运维手动更新数据。

## 11. README 与对外文档

README 是插件的第一印象，读者是服主和其他想用这个插件的人，不是维护者。

- 优先用中文写。结构按正常的开源插件仓库来：banner、简介、功能特性、环境要求、安装、快速开始、命令与权限、配置、开发者 API、FAQ。
- 简介和卖点从服主、玩家的视角描述效果，不要堆算法名和实现术语；确实需要用到术语时，要么解释清楚，要么换成中文说法。
- 不要写实现细节和开发过程（协议量化、插值算法、测试通过数量、实机验证记录等），这些对使用者没有意义。
- 不要写会随版本过时的信息，例如插件版本号；版本兼容性写成 `26.1.2+` 这样的下界形式。

## 12. 验证

单元测试不能替代实机验证，涉及客户端表现的部分只有进游戏才能确认。

- 在本地起对应版本的 Paper 服务器实机验证；声称支持 Folia 时，Folia 端也要实机跑一遍。
- 需要自动化客户端时，可以用 horizon 作为测试客户端。horizon 是一个 Rust 重写的 Minecraft 客户端，和 Java 版号称 100% 兼容（当然，肯定不是 100%）。horizon 的好处是提供了 cli 和 mcp，可以很方便的控制它。
